### 1.2 现状读数纪律（跨文件同源）

1. **凡需证明「数据未变」的现状读数与红线判据，一律用内容指纹，禁用数据库文件 md5**——库处于 WAL 时，`yinpu.db` 的**文件** md5 会在**内容无任何变化**的情况下漂移，而同刻内容口径逐字节未变。**判负形态**：① 以「库文件 md5 不等」判「数据被改」；② 要求复检者提交**库文件 md5** 作为通过判据；③ 用 `sqlite3` CLI + md5 在 WAL 库上取数（得空输入的假结论）。本条与 `ctrl/PORTS.md` 制度 (f)、`xiai/feicui/docs/feicui.spec.md`、`xiai/docs/yinsuo-web.spec.md` **同源**。
2. **「现状 / 事实」类段落必须以磁盘实测或可复算命令输出为准**，并**标注核验时点与证据来源**；**不得从派单 / 聊天 / 口述转述照抄**。派单与磁盘事实不一致时**以磁盘事实为准**，差异登记入本文件的报告与 §11。
3. **未实测的项一律如实标注「未实测」**，不得以推断冒充实测（伪造成功＝红线）。

### 3.5 数据模型归属（R-7 ＋ **V-2 口径**）

- **数据结构以玺爱为主**：**玺爱定义 canonical schema**；**斐萃（feicui）此前的库结构并不完善，后者向前者靠**。**斐萃是待改造的入库管线**；**玺爱是数据归宿**（Zang 裁定 R-7：以后斐萃的数据均存入玺爱的数据库）。
- **方向纪律**：斐萃既有表（`stamps` / `seals` / `images` / `export_batches` / `export_records` / `jobs`）的字段**仅作为「斐萃旧结构 → 玺爱 canonical」的入库映射来源**（映射表见 **§4.4**）；**不得**反过来让玺爱迁就斐萃（**判负形态见 §4 开头**）。**原「数据模型对齐斐萃 / 印面记录字段命名对齐斐萃 `seals` 表」的表述已被 v1.1 取代**（改由 §4.1 定义 canonical、§4.4 承载映射）。
- 层级：**印章 1 对 N 印面**；**边款是一种特殊印面**（`kind = EDGE`）。
- 影像：`kind` 取值 **FACE** 或 **EDGE**，另带 **`sha256` / `bytes` / `width` / `height` / `colorMode`**（canonical 定义为 **§4.1.3 `asset`**；斐萃 `images` 表仅为其**入库映射来源**）。

### 5.1 数值表（**唯一写值处**，其余位置一律引用本节）

| 勘误被采纳 | **奖励 10 金** | **每条**被采纳的勘误**只奖一次**（见 §7） |

**口径数值唯一性**（§1.3 第 8 条）：端口、积分、初始余额等数值**只在本文件写一处**（本表）；页面文案中的数字**须由同一处派生 / 插值**，**不得在组件里硬编码**。

### 5.2 下载计费维度＝**印章**（需求原文，逐字）

> 「同一枚印章，无论下载多少印面，只算作 1 次下载，本次下载消耗指定数量积分」（§2.1 原文 1）

派生口径：

1. **计费单位是印章，不是印面**：同一枚印章的多个印面，**一次「下载会话」内合计只扣 5 金一次**。
2. **幂等**：**同一印章、同一「下载会话」内的重复点击不得二次扣费**——重复点击**要么被判定为同一会话（不再扣费），要么明确提示已扣费 / 已下载**；**不得**每次点击各扣一笔。
3. **「下载会话」的边界由实现侧定义并写入 README**（本文件只定「同会话幂等」这一判据，见 §10 对应 AC）；**跨会话是否再计费不在本版冻结范围**（如需冻结，走 §1 变更流程）。
4. **流水条数**：一次成功下载**只产生一笔** `下载消耗` 流水（金额 `-5`）；**同一会话的重复点击不得新增流水**。

### 5.3 余额不足拦截

- **拦截点**：余额 < 所需金额时，**数据层（services）必须先拦截**——**不得**先扣成负数再回滚、**不得**以「下载失败但已扣费」收场。
- **用户可见反馈**：给**可读提示**（说明所需金额与当前余额），**不得**只抛技术错误码 / 静默失败。
- **副作用为零**：被拦截的下载**不产生流水**、**不改余额**、**不记下载次数**。
- **判负形态**：拦截缺失（余额被扣成负数）；拦截在数据层缺位（仅 UI 层禁用按钮即为缺位——**UI 禁用不能替代数据层拦截**）；拦截后仍写入流水 / 仍改动余额。

### 5.4 积分流水（`ledger`）口径

- **字段**：见 §4.1.6；**金额带符号**（消耗为负、奖励与赠送为正）、**类型枚举只三类**（`下载消耗` / `勘误奖励` / `初始赠送`）、**每笔必带「变更后余额」**。
- **可复算**：任意时点的余额应能由「初始 50 + 全部流水金额」逐笔复算得到；**「变更后余额」与复算结果不一致即判负**。
- **页面**：`/points` 积分中心展示「金」收支流水（见 §8）。

## 7. 勘误状态机

### 7.1 三态（冻结）

| 状态 | 取值 | 说明 |
| --- | --- | --- |
| 待审核 | `PENDING` | 提交后的初始态 |
| 已采纳 | `ACCEPTED` | 管理员采纳；**触发奖励** |
| 驳回 | `REJECTED` | 管理员驳回；**不奖励** |

**状态迁移**：`PENDING → ACCEPTED`、`PENDING → REJECTED`（**单向**）。**终态不得回退**（`ACCEPTED` / `REJECTED` 不得改回 `PENDING`）；**如需更正，须另提一条新勘误**（保留全部历史轨迹）。

### 7.2 不覆盖原始数据（红线）

- **提交勘误不覆盖原始数据**——`face` 的可标记属性**保持原值**；勘误是**旁路记录**（`correction` 表），**不是**对 `face` 的写入。
- **采纳也不覆盖**：即使勘误被采纳，**原始数据逐字节不变**；展示层可以按可信度汇总后**对外展示派生值**，但**底稿不动**。
- **判负形态**：提交 / 采纳后 `face` 的可标记属性值发生变化；或无法从数据层区分「原始值」与「勘误派生值」。

### 7.3 同一字段多条勘误：可信度汇总

- **同一字段多条勘误由平台按「可信度」汇总后对外展示**（不逐条并列刷屏，也不静默丢掉任一条）。
- **演算法本身属待裁项**（见 §11 **W-3**）；本文件冻结的是：**汇总结果必须可复算**（给定同一批勘误与同一算法，任何人可算出同一结果）与**必须可追溯到具体勘误条目**。
- **不覆盖原始数据**依然成立：汇总结果只影响展示，**不改 `face` 原值**（§7.2）。

### 7.4 奖励（采纳奖 10 金）

- **每条被采纳的勘误奖励 10 金**（数值唯一来源＝§5.1）。
- **只奖一次（幂等）**：同一条勘误**被采纳只触发一笔** `勘误奖励` 流水；**重复采纳 / 重复点击审核通过不得二次发奖**。
- **驳回不发奖**；**被拦截 / 失败的审核动作不产生流水**。
- **判负形态**：同一条勘误产生两笔 `勘误奖励`；或驳回后余额仍增加；或奖励金额 ≠ 10 金。

### 7.5 管理员专区须含「勘误审核」页签（Zang 裁定，需求原文未写）

- **依据**：「审核通过后奖励积分」（§2.1 原文 2）**必须有审核点**。
- **要求**：`/admin` 管理员专区**必须含「勘误审核」页签**——在该页签内可查看 `PENDING` 勘误、并执行采纳 / 驳回；**审核动作是 §7.4 奖励的唯一触发路径**。
- **判负形态**：管理员专区无「勘误审核」页签；或存在奖励产生路径但不经审核动作；或审核页签内看不到 `PENDING` 条目。

印文简体字、印文古字、朝代、分类、作者、印文释义、**勘误依据（选填）**（见 §8 / §3.9）。**字段超出此集合即判负**（多出的必填项会让既有勘误不可提交）。
